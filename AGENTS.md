# Repository rules

These rules apply to all work in this repository. Explicit user instructions take precedence. Apply these constraints when using design skills, templates, generators, and external examples.

## Styling: Tailwind classes only

- Author UI styling exclusively through Tailwind utility classes in `className`.
- Reuse `cn()` from `src/lib/utils.ts`. Typed class maps, variant functions, and utilities returning complete Tailwind class strings are encouraged. Keep class names statically discoverable; do not construct fragments such as `bg-${colour}-500`.
- Centralize brand/style decisions in TypeScript class maps and reusable component variants. Feature code should consume these rather than repeat arbitrary colour values and long shared class strings.
- Do not author plain CSS, CSS Modules, Sass, Less, CSS-in-JS, styled JSX, `<style>` elements, inline `style` props, or JavaScript that writes CSS properties. Do not use Tailwind `@apply`, `@theme`, `@utility`, or authored `@keyframes` blocks as a workaround.
- `src/app/globals.css` is a build entry only: `@import "tailwindcss";`. It must not contain authored selectors, declarations, theme blocks, or additional style imports. Tailwind's generated output and framework-generated font/image styles are build/runtime output, not authored application CSS.
- Use Tailwind responsive, state, data/ARIA, transition, animation, and `motion-reduce:` variants. Discrete zoom states must map to complete Tailwind classes. Do not introduce animation objects as another way to author inline styles.
- Third-party Embla transforms are permitted only inside the owned `Carousel` adapter for the user-requested library carousel. Configure the engine through its documented API; do not patch its DOM/styles or author inline styles. All owned layout and visual styling stays in Tailwind class maps.
- Third-party internal page-turn transforms are necessary for the flipbook. They may be generated by the library and isolated behind `MenuBook`; do not patch library DOM/styles or author separate CSS for it. Use documented engine options and Tailwind classes on owned elements.
- Configure shadcn with `tailwind.cssVariables: false` and adapt generated components to this policy. Reject generator-added CSS files, CSS variables/theme blocks, and animation stylesheet imports. Install only components actually needed.

## UI: compose primitives and reusable components

- Pages, layouts, and feature components must compose exported primitives and reusable components. Do not author intrinsic JSX tags such as `<div>`, `<section>`, `<h1>`, `<p>`, `<button>`, `<a>`, `<img>`, or `<input>` in those files.
- Native tags belong only in focused primitive implementations under `src/components/ui/`. The required `<html>` and `<body>` document shell in `src/app/layout.tsx` is the sole framework exception; its contents still use components.
- The boundary applies to equivalent bypasses: lowercase intrinsic `createElement()` calls, `motion.div`/`motion.article`, `asChild` wrapping raw tags, injected HTML, and arbitrary JSX tag factories in feature code.
- Wrap Next.js `Link` and `Image` in reusable link/media primitives. Build interactive controls from shadcn primitives. Render icons through the shared icon primitive; hand-authored SVG belongs inside that primitive.
- Provide meaningful reusable layout primitives such as `Container`, `Section`, `Stack`, `Inline`, `Surface`, `Main`, `Navigation`, `SiteHeaderFrame`, `SiteFooterFrame`, `Article`, `List`, and `ListItem` as their use cases arise. Keep semantics, layout defaults, and accessibility in the primitive. Avoid unnecessary wrappers and one-off aliases that add no reusable behavior.
- Maintain semantic HTML inside primitives: real headings, landmarks, links, buttons, lists, and forms. Use links for navigation and buttons for actions; preserve heading order and avoid nested interactive controls.
- Primitives must forward appropriate native attributes, event handlers, refs, ARIA/data attributes, and `className`. Keep client boundaries limited to components that need browser behavior.

## Typography is owned by this repo

- Create and maintain `src/components/ui/typography.tsx`; do not assume shadcn supplies an importable `Typography` component.
- Use `Typography` for headings, paragraphs, captions, inline text, and quotations. Existing compound primitive text parts such as `DialogTitle` remain valid; they must use the shared typography styles internally.
- Keep visual `variant` independent from semantic `as`: for example, `<Typography as="h1" variant="display">`. Use a restrained typed API, with shared variants for display, title, heading, subheading, body, lead, small, and caption.
- Keep tone, size, weight, responsive behavior, and wrapping rules in reusable Tailwind class maps. Do not duplicate heading/body styling in feature components.
- Preserve Vietnamese diacritics, readable mobile text, appropriate contrast, and accessible semantics. Forward refs and normal text-element attributes.
- Render stored editorial content through a safe rich-text component mapping supported content nodes to owned primitives. Do not bypass the component rule with `dangerouslySetInnerHTML` or unsanitized HTML.

## Trixie product constraints

- Preserve the real Trixie logo/identity and use authentic venue/artist imagery.
- Keep the flipbook as the primary menu experience. Use the latest 18 original menu pages from `trixie.com.vn`, preserving their artwork and complete proportions.
- Desktop supports a book spread; mobile supports readable single pages. Provide category/page navigation, zoom, expand, button/keyboard operation, and reduced-motion behavior.
- Translate navigation and viewer controls through the existing `next-intl` setup. The preserved bilingual menu artwork does not change with the interface language.
- Use verified show information and venue-local time formatting. Do not invent dates, prices, artists, capacity, availability, or successful bookings.
- Keep admin authorization/persistence separate from the public visual redesign.

## Implementation and verification

- Reuse Next.js, React, TypeScript, Tailwind, next-intl, Supabase, and the existing page-turn engine. Add shadcn primitives and their required dependencies deliberately; avoid a framework rewrite.
- Build primitives first, then reusable feature components, then route compositions. Follow `docs/superpowers/specs/2026-10-26-trixie-redesign-design.md` and the current implementation plan.
- Existing code predates these rules. Do not copy its CSS, inline styles, raw-tag composition, or mock-data behavior into new work. Migrate existing violations as part of the redesign; do not claim the current app already complies.
- Add automated checks for intrinsic-tag boundaries, authored styles, and the import-only Tailwind entry during the foundation phase. Exempt only the exact paths and framework tags stated above; do not add broad lint disables.
- Verify lint, TypeScript, production build, and browser interactions at 390/768/1440px. Inspect real screenshots in both languages and test keyboard/reduced-motion behavior.
- Do not claim that rules are mechanically enforced until the checks exist and run successfully. Do not claim build/test success from an earlier run.
- Preserve unrelated user changes, including the existing `.env.example` modification. Do not commit or publish changes without an instruction to do so.

## Public interface clarity

- Avoid duplicate actions or repeated information within the same section. When an embedded widget already provides an action, do not add another equivalent control next to it (for example, a directions link beside Google Maps’ Open in Maps control).
- Keep demo explanations and implementation disclaimers out of the public page unless the user explicitly asks for them. Preserve truthful UI behavior: never invent a successful booking or submission.
