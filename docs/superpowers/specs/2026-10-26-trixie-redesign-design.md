## Art direction

**Recommendation: emerald editorial hospitality.** Take the green and warm light colours from the actual printed menu, preserve the gold logo, and pair them with deep charcoal for evening performances. Use generous but purposeful spacing, strong headings, clear dates, and large photographs. Use flat colours; keep ornament inside the existing artwork rather than repeating its checker pattern across every surface.

Alternative directions are a predominantly dark evening lounge, which gives performers more drama but can diminish the daytime café, or a bright café editorial site, which makes browsing lighter but gives live music less presence. The recommended direction gives the light menu and evening performance imagery equal weight within one system.

Suggested tokens to validate in the first visual pass: emerald `#006B57`, warm paper `#FFFAE7`, charcoal `#15201C`, white `#FFFFFF`, and muted gold `#A18B47`. Use charcoal on paper and paper on emerald for primary text/action pairs. Gold is an identity/detail colour; small gold text requires a checked contrast pair. Use one spacing scale, one container grid, a restrained radius scale, and a consistent icon style.

Implement these choices as complete Tailwind classes in typed TypeScript maps and primitive variants, not CSS variables or theme blocks. Configure shadcn with `tailwind.cssVariables: false`. The only stylesheet content is the Tailwind build import. Apply the font generated by `next/font` through a component class rather than authoring font CSS.

Use Be Vietnam Pro for interface and body copy, with a Vietnamese-capable display face considered only if the visual proof benefits from it. Preserve the logo as artwork. The menu's printed text remains intact and does not change when the site language changes; translate viewer controls and navigation. Headlines should fit within two lines where practical without shrinking body text below readable sizes.

The central idea: **Trixie's printed menu becomes the visual anchor for a modern visit-planning experience, from choosing a drink to choosing a performance.** The flipbook is the signature interaction. Do not add auto-turning or scroll effects that interrupt reading.

## Flipbook experience

Desktop: a deliberate menu workspace with a clear page title, a compact category/page index beside a large two-page spread, and a toolbar containing previous/next, page position, zoom, and expand controls. The cover remains a single page. Keep full images visible using their actual proportions; do not crop menu content with `object-cover`.

Mobile: a single page sized to the available width, an accessible category selector, a compact page count, and previous/next controls with comfortable tap targets. Preserve normal vertical page scrolling. Swipe is optional, with buttons always available. Do not recreate the desktop sidebar or floating vertical booking tab on a phone.

Specific behavior:

- Category jumps and thumbnails go directly to the mapped physical page, with a visible active state. Build the map from inspected artwork; do not assume the current mock categories match the latest scans.
- Treat content pages, covers, and desktop spreads explicitly when computing position and previous/next boundaries. Announce page changes with a concise status message.
- Keep the selected page in the URL so a guest can share or restore it; clamp invalid page values safely.
- Zoom opens a readable original-page view with zoom in/out/reset and normal scroll/pan access. It must not trigger a page turn. Use an accessible dialog with Escape/close, focus containment, and focus restoration.
- Expanding the viewer works in a dialog even when the browser Fullscreen API is unavailable; use native fullscreen only as an enhancement.
- Offer keyboard previous/next while the viewer is focused, without capturing arrow keys inside text fields or the zoom dialog.
- Respect reduced motion with immediate page navigation or a static page viewer if the flip library cannot eliminate its animation cleanly.
- Show a useful loading state and a retry/open-image alternative for a failed page. Preserve access to the original images when JavaScript is unavailable.
- Load the current and neighboring pages efficiently; avoid forcing all original-resolution images into the initial page load.
- Existing artwork is preserved. Any supplemental accessible text must be transcribed from the selected menu version; do not reuse conflicting mock prices or claim that image-only text is screen-reader accessible.

Suggested component responsibilities: `MenuViewer` coordinates page state and responsive mode; `MenuBook` wraps the existing `react-pageflip` engine; `MenuIndex` provides category/thumbnail navigation; `MenuToolbar` provides controls/status; `MenuZoomDialog` handles readable enlargement. These components compose owned primitives and shadcn components instead of intrinsic tags. Keep engine-specific references inside the viewer boundary. Library-generated transforms stay internal; viewer/zoom states use discrete Tailwind class maps instead of authored inline transforms.

## Primitive and typography foundation

Put foundational DOM implementations and adapted shadcn components under `src/components/ui/`. Reuse `cn()` and define typed utility maps in `src/lib/ui/`. Add shadcn Button, Dialog, Sheet, Select, Tooltip, and Skeleton as needed, with generated CSS removed/adapted to the Tailwind-only rules. Compose those primitives into feature components under the existing layout/lounge directories.

Own `Typography` with independent semantic `as`, visual `variant`, and `tone` props, ref forwarding, native attributes, and Tailwind class merging. Initial variants are display, title, heading, subheading, body, lead, small, and caption. The default semantic element is `p`; headings explicitly specify their level. Examples of the intended composition API:

```tsx
<Section aria-labelledby="menu-heading">
  <Container>
    <Stack gap="lg">
      <Typography as="h1" variant="display" id="menu-heading">
        {t('title')}
      </Typography>
      <MenuViewer pages={pages} />
    </Stack>
  </Container>
</Section>
```

Add reusable link/media/icon primitives and semantic layout primitives as required. Compound primitive text parts reuse the typography maps. Stored article HTML is sanitized/parsed into supported nodes rendered by primitives, rather than injected as raw HTML. Enforce these boundaries using source/AST checks; JSX wrappers must preserve proper landmarks, keyboard operation, image alternatives, and heading order.

## Whole-site experience

Shared shell: a simple Trixie logo, understandable navigation, bilingual switcher, and prominent `Đặt bàn` action. Use a dedicated accessible mobile navigation dialog. Keep admin out of the public navigation. Footer contact/help appears consistently across routes.

| Area | Proposed experience |
| --- | --- |
| Home | Real stage/venue imagery, a short Trixie introduction, visible reservation action, upcoming shows, a prominent flipbook preview, café/lounge story, curated photos, and visit details. |
| Menu | The full flipbook workspace described above; the menu artwork is the focal point. |
| Events | Chronological upcoming shows, legible date/time and performer names, uncropped poster access, and event-specific booking context. Separate past shows from upcoming ones. |
| Show details | Clear date/time, performer, real poster, venue, source-provided seating plan when available, and reservation contact. Use verified source details. |
| Journal and articles | Consistent typography, real thumbnails when present, comfortable reading widths, publication dates, related navigation, and sanitized article content. |
| Venue/photos | A curated view of café, lounge, and performance imagery with accessible enlargement; avoid an unfiltered wall of old albums. |
| Private events and contact | Concise service/contact information, venue imagery, directions, and an enquiry action. Do not invent capacity, packages, or prices. |

Prioritize current routes plus show detail and contact/venue information. Venue/gallery/private-event content can start as substantial linked sections on home; dedicated routes are only necessary when enough verified content exists. Admin remains a separately scoped functional project; a visual refresh must not imply that its save/publish controls work.

Use one verified event source across home and events, retaining explicit time zone information. Never calculate fictional future shows from the current date. When no verified upcoming shows exist, show the empty state and reservation contact. Keep venue contact information in one shared content source.

Reservation default: a direct call action using the original site's hotline. A genuine booking form requires a receiving endpoint/workflow before activation. Preserve selected show context wherever it can actually reach the recipient; never simulate a booking confirmation or advertise live seat availability without data.
